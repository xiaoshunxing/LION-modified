# 第一部分：原版 LION 概况

原版 LION 是一个 NVDA 全局插件，按固定间隔对屏幕上某个区域做 OCR，只有在文本变化时才朗读。
用来读视频字幕（YouTube / Netflix / 哔哩哔哩 / 本地播放器 / 直播电视），也能盯住读屏拿不到的文字（如游戏菜单）。

原版的核心设计：

| 维度 | 原版做法 |
|---|---|
| 识别后端 | 随插件携带 `PaddleOCR-json.exe`（296 MB）+ 模型，用 `subprocess` 管道通信 |
| 识别范围 | 单一区域：`target`（导航对象/全屏/当前窗口/当前控件）+ 四个百分比裁剪 |
| 去重 | `SequenceMatcher(None, prev, cur).ratio() < threshold` 才朗读 |
| 过滤 | 用正则从拼接文本里删掉匹配内容 |
| 依赖 | 插件内捆绑 PIL（13.9 MB） |
| 热键 | `NVDA+Alt+N` |
| 许可 | GNU GPL v2 或更高版本；作者 Stefan Moisei、Cary-rowen、anmi2004、hf1324 |

原版的主要约束：插件体积 310 MB、必须有本地引擎进程、只能识别一个区域、多区域时无法同时朗读。

# 第二部分：修改版改动

## 一、修改版做了什么

| | 原版 LION 3.3.0 | LION 修改版 3.3.6 |
|---|---|---|
| 识别后端 | 内置 `PaddleOCR-json.exe`，`subprocess` 管道通信 | 外部 PaddleOCR HTTP 服务，`POST /ocr` |
| 识别范围 | 单一区域 | **多选区列表，可增删改排序、逐个勾选** |
| 去重方式 | 只有相似度 | **每个区域四选一**：经典 / 稳定后朗读 / 跟读增量 / 关闭 |
| 朗读 | 始终打断式 | 可选**排队朗读**（`speech.Spri.NEXT`），互不打断 |
| 每个区域的目标 | 全局一个 | **每个区域各自选择**（导航对象/全屏/当前窗口/当前控件） |
| 去重粒度 | 全局一个 `prevString` | **每个区域独立** |
| 失败提示 | 全局只提示一次 | **每个区域各提示一次**，互不影响 |
| 插件 ID | `LION` | `LION-modified`（可与原版并存） |
| 配置节 | `lion` | `LION-modified` |
| 插件体积 | 310.4 MB | **约 75 KB** |
| 第三方依赖 | 捆绑 PIL 13.9 MB + 引擎 296.4 MB | 无（只用标准库 + NVDA 自带 PIL） |

### 关键设计决策及理由

1. **为什么用标准库 `urllib.request` 而不是 `requests`**
   NVDA 自带 `requests` 与 `urllib3`（在 `C:\Program Files\NVDA\library.zip` 内），但那是
   NVDA 内部打包的版本，会随 NVDA 升级变化。插件不该依赖宿主内部库的可用性与版本，
   所以只用标准库。代价是没有连接池（`localhost` 上可忽略），必须自己写超时与错误分类。

2. **为什么删掉捆绑的 `PIL/`**
   包内路径是 `globalPlugins/lion/PIL/`，而代码写的是 `from PIL import ImageGrab`
   ——该导入解析到 **NVDA 自带的 PIL**（`library.zip` 里 105 个 `PIL/*` 条目 + `PIL._imaging.pyd`），
   包内那 13.9 MB 从未生效。

3. **为什么删掉内置引擎而不留开关**
   需求是"改用外部服务"。留一个 296 MB 的双后端会让包体、测试面、配置面全部翻倍。
   需要离线时回退原版 LION 即可（两个插件能共存）。

4. **为什么显式下发三个能力开关为 `false`**
   服务端配置把 `use_doc_preprocessor` / `use_textline_orientation` 设为 `True`（为了让这些开关可用），
   而 PaddleX 的规则是"客户端省略字段 → 按配置执行"。省略会导致每次请求都跑 UVDoc 去扭曲，
   实测 1000×700 区域从 146 ms 涨到 329 ms。

5. **为什么区域列表存成一整条 JSON 字符串**
   NVDA 的 `config.conf.spec` 用 configobj，`list_values=True` 时会把含逗号的字符串拆成列表，
   对"对象数组"这种结构没有好用的表达能力。存成一整条 JSON 字符串后，
   **一次写入是原子的**，用户不会遇到"只改了一半"的区域列表；解析与校验全部由
   `regions.loadFromJson()` 负责，损坏的配置只会退回默认值。

6. **`regions.py` 为什么不导入任何 NVDA 模块**
   区域数学（裁剪、归一化、迁移）是最容易出错、也最值得测的部分。把"基底矩形"的解析
   通过 `resolveBase` 回调注入，就能在普通 Python 下跑 35 个纯逻辑用例，不需要 NVDA 环境。

7. **排队朗读为什么用 `speech.Spri.NEXT`**
   `ui.message(text, speechPriority=...)` 直接支持优先级。`NEXT` 的语义正是
   "等当前这句读完再读"（NVDA `speech/priorities.py` 的注释），因此不需要自己排线程或加延迟。
   关闭排队时用 `NOW`（立即打断），等价于旧行为。

8. **为什么 `SequenceMatcher` 要显式传 `autojunk=False`**
   `difflib` 默认对长度 ≥ 200 的序列启用 "autojunk"，把出现频率超过 1% 的元素当噪声忽略；
   中日韩文本常用字重复率高，长字幕会被误判为高度相似。识别结果通常只有几十个字，
   关掉这个启发式既准确又几乎不增加开销。

## 四、外部服务 API 契约

### 端点

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 免鉴权探活，返回 `{"logId","errorCode":0,"errorMsg":"Healthy"}` |
| GET | `/openapi.json` | 免鉴权。OpenAPI 文档，`paths` 里是实际挂载的端点（3.3.6 用它做模型列表兜底） |
| POST | `/ocr` | PP-OCRv6 快速档，屏幕内容 → 逐行文本 + 坐标 + 置信度（默认端点） |
| POST | `/ocr-acc` | 精确档（medium 模型）；仅当服务以 `-OcrAccurate` 启动时存在 |
| POST | `/layout-parsing` | PaddleOCR-VL 文档解析 → 版面块 + Markdown；小图约 3 s、整页 7–13 s（可选端点） |

**模型列表（3.3.6）**：本服务**没有** `/models` 端点，请求体里也**没有** `model` 字段 —— 模型/产线由启动时的
yaml 决定。客户端按"通行契约优先"探测：`GET /models`（OpenAI 风格，`data[].{id, endpoint}`）→
`GET /v1/models` → 最后回退 `GET /openapi.json` 的 POST 端点枚举。后者的 ID 就是端点路径，
界面会明确标注"列表来源：OpenAPI 端点列表"，不冒充真正的模型列表。

### 鉴权

三种任选其一（大小写不敏感），插件用第一种：

```http
Authorization: Bearer <token>
X-API-Key: <token>
Token: <token>
```

`/health`、`/docs`、`/openapi.json`、`/redoc`、`/favicon.ico` 免鉴权。令牌不对 → **HTTP 401 + JSON**：

```json
{"logId":"xxx","errorCode":401,"errorMsg":"Unauthorized: missing or invalid token",
 "hint":"Set header  Authorization: Bearer <token>"}
```


**令牌校验技巧（3.3.6 的"测试连接"用）**：令牌中间件在路由之前执行，所以发一个**缺少 `file` 的请求体**
（`{"fileType": 1}`）时：令牌错 → `401`；令牌对但请求体不合法 → `400/422`。不会触发真正的推理，
因此对 PaddleOCR-VL 也是毫秒级，比发小图快得多。

### `/ocr` 请求

`Content-Type: application/json`，`file` 是 Base64（也接受图片 URL）。

| 字段 | 必填 | 插件是否发送 | 说明 |
|---|---|---|---|
| `file` | 是 | 是 | Base64 图像内容 |
| `fileType` | 否 | 是（`1`） | `1`=图像，`0`=PDF |
| `visualize` | 否 | 是（`false`） | 返回可视化图；`false` 时不返回 `ocrImage` |
| `useDocOrientationClassify` | 否 | 是（`false`） | 方向分类 |
| `useDocUnwarping` | 否 | 是（`false`） | UVDoc 去扭曲（截图不要开） |
| `useTextlineOrientation` | 否 | 是（`false`） | 文本行方向分类 |
| `textDetLimitSideLen` | 否 | 仅当设置 > 0 | 检测最长边，越小越快（实测 1280 并不更快） |
| `textRecScoreThresh` | 否 | 仅当设置 > 0 | 服务端低分过滤 |
| `returnWordBox` / `logId` | 否 | 否 | 用不到 |

字段集合由 `/openapi.json` 的 `paddlex__inference__serving__schemas__ocr__InferRequest` 核实。

### `/ocr` 响应（只用到的部分）

```jsonc
{
  "logId": "...", "errorCode": 0, "errorMsg": "...",
  "result": {
    "ocrResults": [
      {
        "prunedResult": {
          "rec_texts":  ["助力双方交往", ""],     // 文本；低置信度处会出现空串
          "rec_scores": [0.998, 0.0],
          "rec_polys":  [[[x1,y1],[x2,y2],[x3,y3],[x4,y4]], ...],
          "rec_boxes":  [[x1,y1,x2,y2], ...],
          "textline_orientation_angles": [...],
          "model_settings": {...}
        },
        "ocrImage": "..."        // 仅 visualize=true 时存在
      }
    ]
  }
}
```

**必须过滤空串**：实测 3840×2160 全屏返回 126 行里含 `""` 且 `score=0.0` 的噪声项，
不过滤会让 `" ".join(...)` 产生连续空格，进而被当成"文本变化"触发朗读。

### `/layout-parsing` 响应（3.3.6 起支持）

```jsonc
{
  "result": {
    "layoutParsingResults": [
      {
        "prunedResult": {
          "parsing_res_list": [
            {"block_label": "text", "block_content": "正文内容", "block_order": 1, "block_bbox": [x1,y1,x2,y2]},
            {"block_label": "table", "block_content": "<table>…</table>", "block_order": 2}
          ]
        },
        "markdown": {"text": "# 标题\n…", "images": {...}}
      }
    ]
  }
}
```

插件只取**文本**：按 `block_order` 排序，跳过 `figure/image/chart/seal` 与疑似标记内容（`<table`/`<html`/`<img`/`![…]`），
`score` 统一记为 `1.0`（VL 没有逐行置信度，避免被 `scoreThresh` 误杀）；没有可用版面块时回退 `markdown.text` 按行切分。
空白画面（`parsing_res_list` 为空）返回 `code 100, data []`，不会当成错误。

### 错误语义与错误码映射

| 情况 | 插件 `code` | 语音/日志内容 |
|---|---|---|
| 成功 | `100` | `data` = `[{"text","score"}, ...]` |
| 地址为空或非法 | `901` | `OCR service address is empty or invalid.` |
| 连接被拒 / DNS 失败 / 其它 OSError | `902` | `Connection failed: <原因>` |
| 超时（含 `URLError("timed out")`） | `903` | `Request timed out after <n> seconds` |
| HTTP 4xx/5xx（含 401/400/422/500） | `904` | `Service responded with HTTP status code: <n>. <errorMsg/hint>` |
| 响应不是合法 JSON | `905` | `Invalid JSON response: <原因>` |
| 响应里 `errorCode != 0` | `904` | 服务端 `errorMsg` + `hint` |
| 响应里没有 `ocrResults` | `905` | `No OCR result found in the response.` |

`code != 100` 时主循环调用 `reportFailure(label, regionId=...)`：**每个区域连续失败只在第一次播报**
（受 `notifyOnError` 控制），之后只写 `logHandler.log.error`，该区域成功一次后复位。

## 五、代码导读

### `dedup.py`（3.3.3 新增：四套去重策略，零 NVDA 依赖）

```
MODES = ("classic", "commit", "incremental", "off")     界面下拉框顺序
DEFAULT_HOLD_MS=1500 / HOLD_MIN_MS=500 / HOLD_MAX_MS=10000
MAX_PENDING_SECONDS=10.0                                 永不稳定时的强制释放上限
BOUNDARY_CHARS                                           只认标点，不认空白
_SpeechEvent(text, reason)                               reason 供日志与测试断言
_DedupEngine
    observe(regionId, text, mode, holdMs, now, threshold) -> [SpeechEvent]
    reset() / resetRegion(id) / prune(configuredRegions)
    stateFor(regionId)                                   测试用只读快照
```

**设计要点**

- **不读时钟**：`now` 由调用方传入（插件用 `time.monotonic()`，测试用虚拟时间），
  所以状态机完全可重现，49 项用例能在毫秒内跑完。
- **不做翻译初始化、不导入 NVDA 模块**：这是刻意的，`test_manifest_and_config` 里有专门用例
  防止以后被人加回 `import addonHandler`。
- **classic 分支与 3.3.2 逐字一致**：`similarityRatio(lastSpoken, text) < threshold` 才念。
- **commit 分支**：`holdSince` 记录"文本最后一次变化的时刻"，`now - holdSince >= holdMs`
  且这一段尚未释放过（`released`）时，念 `text[lastSpoken:]`（前缀延续时只念新增部分）。
- **incremental 分支**：先找标点边界，找到就念 `text[watermark:边界]`；
  找不到时退化为"稳定后念剩余"。
- **替换检测**：新文本不再以 `lastSpoken` 开头 → 视为另一句话，`lastSpoken`/`watermark` 归零，
  避免新句被当成旧句的延续而漏读。
- **强制释放**：`now - pendingSince >= 10` 秒时释放一次（`reason="forced"`），
  避免滚动条/动画让区域永不稳定而一句都不念。

### 打字机时间线（虚拟时间实测，`test_dedup.CommitModeTests`）

| 帧 | 输入 | classic | commit（1500ms） |
|---|---|---|---|
| t=1 | 你 | 念"你" | 不念 |
| t=2 | 你好 | 跳过 | 不念 |
| t=3 | 你好冒险者 | 念"你好冒险者" | 不念 |

## 八、本次修复/改进的原版缺陷

### 8.1 正则过滤留下多余空格（3.3.1 已修）

原版：`all_text = " ".join(...)` 之后再 `re.sub`。于是行锚点 `^...$` 匹配不到单行；
即使匹配成功，删掉中间内容也会留下多余空格（`"广告 正文"` → `" 正文"`），
写回 `prevString` 后与下一轮的干净文本产生差异，可能读出空内容或重复朗读。
现在 `filterText()` 在过滤后折叠空白。

### 8.2 相似度去重的 `autojunk` 隐患（3.3.2 已加固）

`difflib.SequenceMatcher` 默认 `autojunk=True`：序列长度 ≥ 200 时把出现频率 > 1% 的元素当噪声忽略。
中日韩字幕常用字高度重复，长句有被误判为"完全一样"从而永不重读的风险。
现在 `similarityRatio()` 显式传 `autojunk=False`，并有 6 个用例锁定去重语义（含阈值 0 与 1 的边界）。

### 8.3 单区域时代的结构性限制（3.3.2 已解决）

- 只能一个区域 → 现在可多区域、可勾选；
- 多区域时无法都朗读 → 现在有排队朗读；
- 全局一个 `prevString` → 现在每区域独立；
- 单区域失败会连带影响整轮 → 现在逐区域隔离。

## 八、3.3.4 修复：OCR 抖动导致的重复播报与整段重读

### 8.1 缺陷一：commit 重复播报

3.3.3 用"整串前缀"判断"还是不是同一句"，并且 `lastSpoken` 同时充当"已播报记录"与"锚点"：

```
if state.lastSpoken and not text.startswith(state.lastSpoken):
    state.lastSpoken = ""        # 一帧抖动就失忆
    state.watermark = 0
```

真实 OCR 每帧都有 1 个字的差异，于是：

```
t=3  你好冒险者欢迎来到新手村  -> 播报
t=4  你好冒险者欢迎来到新手材  -> 前缀失配 -> 已播报记录被清空
t=5  你好冒险者欢迎来到新手村  -> 重新计时 -> 稳定后再播一次（重复）
```

### 8.2 缺陷二：incremental 整段重读

`watermark` 是"位置"锚点，且由同一处逻辑在"新帧不以旧帧全文开头"时清 0。跟读的已播报内容一旦
被清零，`findBoundary(text, 0)` 会返回**整个文本框里最后一个标点**，于是从头念到那里。

### 8.3 缺陷三：10 秒保护打断正常打字

`pendingSince` 原本在"文本变化"时刷新；持续增长的正常台词让它一直为初值 → 第 10 秒触发 `forced`，
把没打完的半句念出来。

### 8.4 修复思路（3.3.4 的 dedup.py）

1. **帧分类** `classifyChange(prev, cur)` → `same / empty / growth / jitter / replace`
   * `growth`：`cur.startswith(prev)`（打字机在继续打）
   * `jitter`：去空白后编辑距离 ≤ 1，且公共前缀占比 ≥ 0.5、长度 ≥ 3（真正的最短编辑距离 DP）
   * 只差"结尾一个 ASCII 数字/字母"的算 `replace`（`第1帧`→`第2帧` 是不同内容）
2. **抖动不清记忆**：`jitter` / `same` 帧只更新 `lastSeen`，不刷新 `holdSince`、不清 `announced`、
   也不作为播报文本。
3. **播报用 `stableText`**（最后一次实质变化的帧），抖动帧的内容永远不会被念出来。
4. **内容锚点**：`announced` 记录"已经播报出去的内容前缀"，跟读用 `commonPrefixSpoken(announced, text)`
   求起点，替代原来的位置 `watermark`。
5. **`_unspokenTail` 判定顺序**：先判"截断/同长抖动"（返回空），再判"前缀延长"（返回新增部分），
   最后才是"整句替换"。
6. **空帧宽限**：连续空帧超过 `max(2s, 2×hold)` 才复位，一帧闪空不再导致整句重念。
7. **兜底计时** `unstableSince`：只在 growth/replace 时重置、jitter 时不重置；正常打字永远不被兜底打断。
8. **切换策略时重建状态**：避免 classic 留下的 `released=True` 让 commit 沉默。

### 8.7 3.3.5：跟读增量的重复播报

3.3.4 之后 `commit` 稳定，但 `incremental` 在句子安定后仍会整段重念。两个原因叠加：

1. **抖动判定用"公共前缀占比"**（`classifyChange` 里 `prefix / length >= JITTER_MIN_PREFIX_RATIO`）：
   长台词靠前位置错一个字时 `3/26 = 0.12`，被判成 `replace`。
2. **`incremental` 拿到 `replace` 就清空 `announced`**，于是 `findBoundary(source, 0)`
   命中第一个标点、从第一个字重念。`commit` 有 `ALREADY_ANNOUNCED_RATIO` 兜底，所以没暴露。

修复（`dedup.py`）：

* `classifyChange` 改为**长度自适应的编辑距离**：
  `JITTER_EDIT_DISTANCE=1`（短句）/ `JITTER_EDIT_DISTANCE_LONG=2`（≥ `JITTER_LONG_TEXT_LENGTH=12` 字），
  长句用 2 处编辑时还要求 `similarityRatio >= JITTER_LONG_MIN_SIMILARITY=0.8`；
  `shortSide < JITTER_MIN_LENGTH=3` 一律 `replace`（`是`/`否` 这类选项不能被吞）。
* 新增 `differenceSnippet(a, b)`：剥掉公共前后缀后看差异片段；**含 ASCII 数字 → `replace`**
  （`第1帧`→`第2帧`、`HP: 100`→`HP: 90` 属状态更新）。
* `commonPrefixSpoken` 增加第三层"**模糊锚点**"：精确前缀与后缀错动都失败时，用
  `SequenceMatcher` 求匹配块，覆盖率达到 `ANCHOR_MATCH_RATIO=0.85` 就返回匹配块末尾作为续读点。
  仅在 `len(spoken) >= ANCHOR_MIN_LENGTH=12` 时启用（短文本冗余不足，模糊锚定会锚错）。
* `_incremental` 补上与 `commit` 对等的
  `similarityRatio(announcedFull, source) >= ALREADY_ANNOUNCED_RATIO` 兜底。
* 新增 `hasSpeakableContent()`：纯标点片段不单独播报（`announced` 仍推进，不会重试）。

| 常量 | 值 | 作用 |
|---|---|---|
| `JITTER_EDIT_DISTANCE` / `JITTER_EDIT_DISTANCE_LONG` | 1 / 2 | 短/长文本的抖动容差 |
| `JITTER_LONG_TEXT_LENGTH` | 12 | "长文本"门槛 |
| `JITTER_LONG_MIN_SIMILARITY` | 0.8 | 2 处编辑时的相似度下限 |
| `JITTER_MIN_LENGTH` | 3 | 太短不判抖动 |
| `ANCHOR_MATCH_RATIO` / `ANCHOR_MIN_LENGTH` | 0.85 / 12 | 模糊锚点阈值与启用长度 |

## 九、3.3.6：自定义模型（OCR 端点）与模型列表发现

### 9.1 为什么"模型"= 端点

PaddleX 的 serving 是"一条产线一个 app"，模型/产线在**启动时**由 yaml 决定；`/ocr`、`/layout-parsing`
的请求体 schema 里都没有 `model` 字段。3.7.2 的 serving 层也**只注册了 `/health`**，没有 `/models` 端点。
所以客户端唯一能切换的维度是"打哪个端点"，插件把这一维命名为 `model`。

`serviceUrl` 因此从"完整地址"改成"**服务基址**"：

```ini
serviceUrl = http://127.0.0.1:23353   ; 基址（可含反向代理前缀，如 http://host/paddle）
model      = /ocr                     ; 端点路径，或完整 URL（此时基址被忽略）
```

请求地址 = `composeUrl(serviceUrl, model)`：`model` 是完整 URL → 直接用；否则 `基址 + "/" + model`；
`model` 为空 → 退回 3.3.5 的 `normalizeBaseUrl()` 行为（无路径补 `/ocr`）。

**迁移**：`ensureServiceMigrated()` 只在配置里没有 `model` 键时执行，调用 `splitServiceUrl()`
把旧完整地址拆成 `(基址, model)`；`splitServiceUrl` + `composeUrl` 的组合保证与旧
`normalizeBaseUrl()` 结果一致（8 组往返用例锁定，含 `/paddle/ocr` 这种代理前缀）。

### 9.2 模型列表的三级发现

`HttpOcrClient.listModels()` 按"通行程度"依次探测，返回 `(models, source, error)`：

| 级别 | 请求 | source | 说明 |
|---|---|---|---|
| 1 | `GET /models` | `models` | OpenAI 风格；条目可用 `endpoint`/`path`/`url` 指定真正端点 |
| 2 | `GET /v1/models` | `v1/models` | OpenAI 兼容实现 |
| 3 | `GET /openapi.json` | `openapi` | **兜底**：`paths` 里带 `post` 的端点，排除 `/restructure-pages` |

`parseModelList()` 宽容支持 `data` / `models` 两种列表键，以及 `id` / `name` / `model` 三种标识键；
**没有可路由端点的条目会被丢弃**（Ollama 风格 `/api/tags` 就是这种），因为插件必须知道往哪 POST。
`source == "openapi"` 时设置面板会明确写"列表来源：OpenAPI 端点列表"，不冒充模型列表。

### 9.3 合并按钮：测试连接 + 获取模型列表

`lionGui.onTestAndDiscover()` 一个按钮完成：

1. `listModels()` → 刷新可编辑组合框（显示模型 `id`，内部映射到请求端点）；
2. 失败时先 `testConnection()` 探活，区分"服务不可达"和"服务没有模型列表"；
3. `verifyToken()`：POST `{"fileType": 1}`（缺 `file`）—— 401 说明令牌错，400/422 说明令牌有效，不触发推理；
4. 非 `/layout-parsing` 端点再发 8×8 白图做识别测试；VL 端点跳过并说明（单次 3 s 以上）。

组合框保存的是**请求端点**（`onSave` 里用 `modelEndpoints` 映射），所以配置语义稳定；手填的任意路径或完整 URL 原样保存。

### 9.4 PaddleOCR-VL 的文本提取

`parseResult()` 的形态判定顺序：

1. `prunedResult.rec_texts` 存在 → PP-OCRv6 路径（原有行为，过滤空串与 `scoreThresh`）；
2. `prunedResult.parsing_res_list` 存在 → 按 `block_order` 排序取 `block_content`，跳过
   `figure/image/chart/seal` 与 `<table`/`<html`/`<img`/`![` 开头的标记内容，`score = 1.0`；
3. 没有可用块 → `markdown.text` 按行切分；
4. 条目存在但都没有文本 → `100/[]`（空白画面不是错误）；两种结果结构都不存在 → `905`。

### 9.5 涉及文件

- `ocrClient.py`：`normalizeServiceBase` / `normalizeModel` / `composeUrl` / `splitServiceUrl` /
  `parseModelList` / `parseOpenApiModels` / `openapiUrl` / `_getJson`；`HttpOcrClient(..., model=)`、
  `listModels()`、`verifyToken()`、`parseResult()` 的 VL 分支。
- `__init__.py`：`confspec` 新增 `model`（14 项）、`serviceUrl` 默认改基址、`ensureServiceMigrated()`、
  `makeOcrClient()` 传 `model`。
- `lionGui.py`：可编辑 `wx.ComboBox`、合并按钮 `onTestAndDiscover`、`setModelChoices` / `modelTarget`。
- **未改动**：`dedup.py`（与 3.3.5 打包态字节一致）、`regions.py`、服务端（本机部署）。

### 9.6 明确不做的事

- 不改造服务端、不新增 `/models`、不写服务端补丁；`/models` 探测是对其它/未来兼容服务的预留。
- 不分别适配两条产线的高级特性（版面、表格、公式、图表、印章）；只取"文本行"这个共性。
- `detLimitSideLen` / `scoreThresh` / `visualize` 对 `/layout-parsing` 无效（服务端忽略），保持设置原样并在文档写明。

## 十一、与原版共存：机制与注意事项

- **插件 ID 唯一**：NVDA 用 `manifest.ini` 的 `name` 作为唯一键（见
  [addonHandler](https://github.com/nvaccess/nvda/blob/release-2026.2/source/addonHandler/__init__.py) 的
  `AddonBase.name`），安装目录由 ID 决定，互不覆盖。
- **配置节独立**：`LION-modified` vs `lion`。
- **翻译独立**：`.mo` 按插件自身路径加载（`Addon.getTranslationsInstance`）。
- **设置面板可区分**：分类名取面板类自己的 `title`（`gui/settingsDialogs.py` 的 `SettingsPanel.title`），
  中文界面下分别显示"LION"与"LION 修改版"。
- ⚠️ **热键冲突**：两个插件都绑 `NVDA+Alt+N`。NVDA 的手势映射是全局命名空间，
  `scriptHandler._findScript` 按对象顺序取**第一个**匹配的脚本，因此这是"无法预期触发哪个"的冲突绑定。
  用户必须二选一：在"输入手势"里清除原版的 `NVDA+Alt+N`，或给其中一个改绑别的键。
  **文档（readme）与交付说明都必须写清这一点。**

## 十二、扩展点（留给下一步）

1. **接入 `/layout-parsing`（文档解析）**：`ocrClient.parseResult` 已兼容
   `result.layoutParsingResults[0].prunedResult.rec_texts`；做"整页 → Markdown"需要新增读取
   `markdown.text` 的方法与独立热键（整页 7–10 s，不能放进 1 秒循环）。
2. **区域坐标可视化**：现在只能靠百分比估算。可加"按当前目标预填坐标/预览矩形"的助手。
3. **按区域覆盖全局设置**：目前 `threshold`/`regexFilters`/`interval` 是全局的；
   若某些区域需要不同阈值，可在区域对象里加可选字段（`loadFromJson` 已经是易扩展的字典结构）。
4. **连接复用**：现在每个请求新建 TCP 连接。`localhost` 上可忽略；服务在远端时可换长连接。
5. **失败退避**：现在失败后下一轮照常重试；可在 `reportFailure` 里加指数退避。
6. **代理支持**：`urllib` 默认遵循系统代理；需要时显式设置 `no_proxy`。

## 十三、已知限制与风险

| 限制 | 说明 | 影响 |
|---|---|---|
| 必须有外部服务 | 插件不含引擎 | 服务没起时完全不可用（每区域提示一次 + 日志） |
| 行序非阅读顺序 | `rec_texts` 是检测顺序，插件按顺序空格拼接 | 字幕无影响；整页文档需要 `/layout-parsing` |
| 多区域线性增加耗时 | 一次只有一个请求在飞 | 区域越多越大越慢，请只勾选需要的 |
| 排队朗读的队列不会因"停止识别"清空 | 已入队的文本会读完 | 文档已写明；插件禁用/NVDA 退出时会 `cancelSpeech` |
| 未在 NVDA 进程内实跑 | 当前只做离线验证，未安装插件 | 代码路径由 58 项集成用例 + 静态检查覆盖；**首次真实安装后请确认面板与热键** |
| 手势冲突 | 与原版同键 | 必须手动解绑（见第九节） |
| 令牌明文存在 `nvda.ini` | NVDA 配置本来就是明文 | 多人共用机器时注意配置目录权限 |
| 服务监听 `0.0.0.0` | 局域网可达，仅令牌保护 | 插件支持指向远端，但请注意网络暴露面 |
